# WaterAPI | 시설 점검과 AI 분석

시설과 점검일지를 관리하고, 점검 내용을 분석해 위험도와 권장 조치를 확인하는 개인 웹 프로젝트입니다. 점검 내용이 바뀌었을 때 기존 분석을 어떻게 처리할지와 데이터를 올바르게 저장하고 조회하는 데 집중했습니다.

**Java 17, Spring Boot 4.1, Spring Data JPA, Thymeleaf, MySQL, OpenAI, Docker, AWS**

## 해결한 문제

### 1. 점검 내용과 분석 결과가 어긋나는 문제

- **문제:** 점검 내용을 수정해도 이전 내용의 분석이 남으면, 사용자가 잘못된 결과를 참고할 수 있습니다.
- **해결:** 점검일지 수정과 기존 분석 삭제를 하나의 트랜잭션으로 묶었습니다. 수정 후에는 사용자가 새 내용으로 다시 분석할 수 있습니다.
- **확인:** 실제 MySQL에서 분석 삭제 오류를 발생시킨 뒤, 서비스 처리가 끝나고 DB를 다시 조회했습니다. 점검 내용과 날짜, 기존 분석이 모두 수정 전 상태로 유지되는 것을 확인했습니다.

### 2. 목록에서 시설 정보를 반복 조회하는 문제

- **문제:** 점검일지 목록에 시설명을 표시하면서 시설 조회 SQL이 추가로 발생했습니다.
- **해결:** 목록 조회에 `EntityGraph`를 적용해 점검일지와 시설을 함께 가져왔습니다.
- **확인:** 서로 다른 시설을 연결한 점검일지 30건 중 첫 페이지 10건을 조회할 때 **SQL 실행 횟수가 12회에서 2회로 줄었습니다.** 조회 결과, 정렬, 전체 건수도 동일했습니다. 측정한 값은 응답 시간이 아닌 SQL 횟수입니다.

## 주요 흐름

1. 시설을 등록하고 해당 시설의 점검일지를 작성합니다.
2. 분석 버튼을 누르면 점검 내용의 요약, 위험도, 권장 조치를 저장합니다.
3. 대시보드와 목록에서 점검 처리 상태와 분석 결과를 확인합니다. 점검일지를 수정하면 이전 분석을 지우고 재분석할 수 있습니다.

시설 하나에 여러 점검일지가 연결되고, 점검일지 하나에는 최대 하나의 분석 결과가 연결됩니다. 점검일지가 있는 시설은 삭제를 막습니다.

## 실행하며 확인한 결과

- **AWS 배포:** Docker 이미지를 ECR에 올려 EC2에서 실행하고, 외부에 공개하지 않은 RDS MySQL에 연결했습니다.
- **데이터 유지:** 컨테이너를 새로 만들어도 시설, 점검일지, 분석 결과가 유지됐습니다. 데이터는 앱 이미지 안이 아니라 별도 RDS에 저장되기 때문입니다.
- **테스트:** GitHub Actions에서 일반 테스트, MySQL 테스트와 실행 검증이 통과했습니다. AWS 배포는 수동으로 진행했습니다.

실제 OpenAI 호출은 로컬 Docker에서 확인했습니다. AWS에서는 정해진 분석 결과를 반환하는 **Stub**으로 업무 흐름을 검증했습니다. 인증과 권한 기능은 아직 구현하지 않았으며, 상시 공개 서비스는 운영하지 않습니다.

## 로컬에서 확인하기

Java 17을 설치한 뒤 저장소 폴더에서 실행합니다. 기본 실행은 H2 파일 DB와 Stub을 사용하므로 별도 DB나 API 키가 필요 없습니다.

```powershell
.\gradlew.bat bootRun
```

브라우저에서 `http://localhost:8080`에 접속합니다. Linux와 macOS에서는 `bash gradlew bootRun`을 사용합니다.
