# WaterAPI 핵심 설명

**이 문서가 필요한 이유:** 루트 README에 적은 기능과 개선 결과를 내 말로 설명하기 위한 짧은 보충 자료입니다. 먼저 [프로젝트 소개](../README.md)를 보고, 아래 네 가지를 이해한 뒤 [확인 결과](VERIFICATION.md)를 읽습니다.

## 1. 요청이 들어오면 어디서 처리하나요?

Controller는 입력을 받고 검사합니다. Service는 점검 등록, 수정, 분석 같은 업무 규칙을 처리합니다. Repository는 DB 저장과 조회를 담당합니다. 조회한 데이터는 Thymeleaf 화면에 표시합니다.

시설 하나에는 여러 점검일지가 있고, 점검일지 하나에는 최대 하나의 분석 결과가 연결됩니다. 점검일지가 있는 시설은 삭제하지 못하게 했습니다.

## 2. 점검일지를 수정하면 왜 분석도 지우나요?

점검 내용이 달라졌는데 이전 분석이 남아 있으면 사용자가 잘못된 결과를 볼 수 있기 때문입니다. 수정 요청이 성공하면 기존 분석을 삭제하고, 사용자가 다시 분석하도록 했습니다. 점검의 처리 상태는 그대로 유지합니다.

수정과 분석 삭제는 하나의 **트랜잭션**, 즉 함께 성공하거나 실패해야 하는 작업 단위로 묶었습니다. 분석 삭제가 실패하면 점검 내용과 날짜 변경도 취소됩니다. 예외 발생 여부뿐 아니라 서비스 처리가 끝난 뒤 DB를 다시 조회해 이를 확인했습니다.

관련 코드: [점검 수정 서비스](../src/main/java/com/kjune922/waterapi/inspection/InspectionReportService.java)

## 3. 목록 조회의 SQL을 어떻게 줄였나요?

점검 목록을 가져온 다음 각 시설명을 따로 조회하면서 SQL이 반복됐습니다. 이런 추가 조회 문제를 **N+1 문제**라고 합니다.

`EntityGraph`로 목록 조회에 필요한 시설 정보도 함께 가져오게 했습니다. 비교 조건에서는 목록 1회, 전체 건수 1회, 시설 10회였던 SQL이 목록과 시설 1회, 전체 건수 1회로 줄었습니다. 실행 시간 대신 SQL 횟수를 비교한 결과입니다.

관련 코드: [목록 조회 Repository](../src/main/java/com/kjune922/waterapi/inspection/InspectionReportRepository.java)

## 4. Stub과 실제 AI는 무엇이 다른가요?

**Stub**은 정해진 분석 결과를 주는 테스트용 대역입니다. API 키 없이도 분석 결과의 저장과 조회 흐름을 확인할 수 있습니다. 실제 OpenAI 연동은 점검 내용을 외부 API로 보내 응답을 받습니다.

둘 다 같은 분석 요청 인터페이스를 사용하고 실행 설정으로 선택합니다. 응답에 필요한 값이 없거나 너무 길면 저장하지 않습니다. 실제 OpenAI 호출은 로컬에서, AWS의 업무 흐름은 Stub으로 확인했습니다.

## 말로 정리해 보기

> 시설과 점검일지를 관리하고 분석 결과를 조회하는 서비스입니다. 점검 내용과 분석이 어긋나지 않도록 수정과 기존 분석 삭제를 함께 처리했습니다. 실패했을 때도 DB를 다시 조회해 원래 데이터가 남는지 확인했고, 목록에서는 시설을 함께 조회해 반복 SQL을 줄였습니다.

위 문장을 읽은 뒤, 문서를 덮고 “왜 분석을 지우는지”, “삭제 실패는 어떻게 확인했는지”, “12회에서 2회가 무엇인지”를 설명해 봅니다.
