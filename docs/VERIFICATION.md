# WaterAPI 확인 결과

## 시설 유형별 점검표 개발 검증

| 개발 환경에서 실행한 검증 | 확인 결과 |
| --- | --- |
| Java 17 · Gradle `clean build mysqlTest` | 일반 테스트 75건과 임시 MySQL 8.4.13 테스트 17건 통과. 실패·건너뜀 0건. |
| 요청 내용·오류 | 저장한 항목 전체와 사유·특이사항·조치가 모의 HTTP 요청의 입력과 일치했고 점검자 이름은 빠졌습니다. 미점검·해당 없음이 그대로 전달됐습니다. HTTP 실패 시 분석은 저장되지 않았고, 오류 안내 후 다시 상세를 열면 DB 상태가 표시됐습니다. |
| 순서가 엇갈린 AI 응답 | MySQL에서 AI 응답을 대기시킨 사이 일지를 수정하자 이전 응답의 저장이 거절됐습니다. 분석을 먼저 저장하고 확정한 뒤 일지를 수정하면 분석 행이 삭제됐습니다. |
| 삭제 실패·동시 확정 | 분석 삭제를 MySQL 트리거에서 실패시킨 뒤 일지·답변·AI 원본·사용자 확정본을 수정 전 값과 비교했습니다. 모두 같았습니다. 동시 확정은 한 요청만 성공했습니다. |
| V2 → V3 이전 | 별도 임시 MySQL의 V2에 자유서술형 일지와 확정 분석을 넣고 V3를 적용했습니다. 기존 일지와 분석 행의 값·시각이 보존됐습니다. 점검자·양식 정보는 비어 있고 답변은 0건이었습니다. |
| Chromium 1440px·390px · H2·Stub | 각 너비에서 네 양식의 등록·오류 후 작성값 유지·수정·관찰 부족 안내·분석 중·검토 대기·확정을 확인했습니다. AI 주의를 사용자 위험으로 확정한 뒤 대시보드 건수와 연결 목록의 전체 건수 및 위험도 표시가 일치했습니다. |

최종 리뷰에서는 상세 조회 변경과 관련된 일반 테스트 23건과 새 MySQL 회귀 테스트 1건이 통과했습니다. 원문 조회 직후 다른 연결에서 일지 수정과 재분석을 커밋해도, 진행 중인 조회는 처음 읽은 원문과 그 시점의 확정본을 함께 반환했습니다.

## AWS 구성을 설명할 때

Docker 이미지를 **ECR**에 올리고, **EC2**에서 앱 컨테이너로 실행했습니다. 데이터는 외부에 공개하지 않은 **RDS MySQL**에 저장했습니다. **SSM 포트 포워딩**으로 내 PC에서 화면에 접속했습니다.

CloudGuard와 서버와 RDS 인스턴스를 함께 사용했지만 DB와 앱 계정은 분리했고, 두 앱은 번갈아 실행했습니다. 테스트 자동화와 AWS 배포는 구분합니다. GitHub Actions에서 테스트를 실행했고, AWS 배포는 직접 진행했습니다.

## 실행과 데이터 보존에서 기억할 것

- 이미지는 앱 실행에 필요한 파일 묶음입니다. `pull`은 다운로드이고, 그 이미지로 컨테이너를 만들어 실행해야 앱이 동작합니다.
- 로컬 MySQL 데이터는 Docker 볼륨에, AWS 데이터는 RDS에 저장했습니다. 앱 컨테이너 교체가 DB 삭제를 뜻하지는 않습니다.
- 앱 이미지를 이전 버전으로 돌려도 DB 데이터가 과거로 돌아가지는 않습니다. 백업 복원은 별도 작업입니다.
- 컨테이너가 Up이어도 기능 성공을 보장하지 않습니다. 헬스체크 후 실제 등록과 조회를 확인합니다. 요청에서 500 오류가 나면 그 시점의 앱 로그에서 예외를 먼저 찾습니다.

**설명할 범위:** AWS에서는 Stub 분석과 데이터 유지를 확인했습니다. 실제 OpenAI 호출, 백업 복원, 이전 앱 이미지 복구는 로컬 결과입니다. 인증과 권한, 무중단 배포는 구현한 범위에 포함하지 않습니다.

실습 종료 후 EC2와 RDS를 중지했고, 11월 20일 Elastic IP를 반납했습니다. 상시 공개 데모는 운영하지 않습니다.
