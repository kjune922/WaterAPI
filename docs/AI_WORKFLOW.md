# AI 분석 검토·확정 작업 기록

## 계획과 구현

먼저 저장소의 분석 저장 흐름과 점검일지 수정 규칙을 조사했다. 사용자가 계획을 검토한 뒤, 점검일지 상세에서 원문과 AI 응답을 비교하고 한 번에 수정·확정하는 기능을 구현했다.

- 기존 분석에는 사람이 검토했다는 기록이 없어 Flyway V2에서 검토 대기로 초기화했다. AI 원본은 보존하고 확정값과 시각은 비워 뒀다.
- 두 번 제출해도 최초 확정본이 남도록 DB에서 검토 대기인 행만 갱신했다. 갱신 후 같은 트랜잭션에서 다시 읽었을 때도 확정값이 보이는지 테스트했다.

## 리뷰에서 바꾼 점

위험도가 잘못됐을 때 서버는 저장을 거절했지만, 오류 화면에서는 첫 선택지인 ‘정상’이 선택된 것처럼 보일 수 있었다. 다크 UI를 적용하면서 빈 값의 ‘위험도 선택’을 추가했다. 최초 검토 화면에는 AI 위험도를 표시하고, 오류 화면에는 사용자가 입력한 나머지 값과 오류 메시지를 유지했다.

개발 중 UI를 변경한 뒤 Chromium에서 다른 필드만 고쳐도 위험도를 선택하기 전까지 확정할 수 없음을 확인했다. 브라우저의 입력 검사를 건너뛴 요청도 서버가 400으로 거절했다.

PR #3 병합 전 사용자가 집 PC의 `feature/analysis-review`에서 두 가지 확정 흐름을 직접 실행하고 화면을 공유했다. AI 원본을 그대로 확정한 경우와 위험도·권장 조치를 바꿔 확정한 경우였다. 병합 후에는 사용자가 로컬 `main`을 업데이트하고 작업 트리와 커밋을 확인했다.

중간 저장과 확정본 직접 정정, 사용자 인증과 담당자별 확정 기록은 지원하지 않는다. [단계별 검증 결과](VERIFICATION.md)

## 시설 유형별 점검표 작업

사용자가 승인한 범위는 네 유형의 고정 점검표, 기존 자유서술형 호환, 저장값 기반 AI 요청, 사용자 확정 위험도 기준의 조회·집계다. 점검자 이름은 직접 입력하며 분석에는 보내지 않는다. 기록 수정과 늦은 AI 응답이 겹칠 수 있어 외부 호출과 결과 저장을 분리했다. 결과를 저장하는 짧은 트랜잭션에서 일지를 잠그고 수정 번호를 확인한다.

펌프 8쪽과 배관설비 23쪽은 사용자가 대화에서 확인해 전달한 항목을 선별했다. Codex 환경에서는 원문 접근이 차단돼 직접 대조하지 못했다. 밸브는 관련 항목을 참고한 자체 구성이고, 수질 센서는 자체 실습 양식이다. 화면에도 출처와 적용 범위를 표시한다. [국가법령정보센터 원본](https://www.law.go.kr/LSW/flDownload.do?flSeq=156037639)

390px 검토 화면에서 긴 상태 문구가 가로로 넘치는 것을 발견했다. 제목과 상태 배지가 다음 줄로 내려가게 수정한 뒤 두 화면 폭에서 다시 확인했다. 이 작업의 실행 결과는 이전 PR의 CI와 구분해 기록했다. [점검표 검증 결과](VERIFICATION.md#시설-유형별-점검표-개발-검증)

최종 리뷰에서 상세 화면의 원문 조회와 분석 조회가 분리된 것을 확인했다. 두 조회 사이에 다른 요청이 일지를 수정하고 재분석하면 서로 다른 시점의 값을 비교할 수 있었다. 상세 조회와 확정 입력 오류 화면은 두 값을 같은 읽기 트랜잭션에서 가져오도록 수정했다. 실제 MySQL에서 두 조회 사이에 수정·재분석을 끝내고도 원문과 확정본이 같은 시점의 값으로 표시되는지 검증했다.
