# AI 분석 검토·확정 작업 기록

## 계획과 구현

먼저 저장소의 분석 저장 흐름과 점검일지 수정 규칙을 조사했다. 사용자가 계획을 검토한 뒤, 점검일지 상세에서 원문과 AI 응답을 비교하고 한 번에 수정·확정하는 기능을 구현했다.

- 기존 분석에는 사람이 검토했다는 기록이 없어 Flyway V2에서 검토 대기로 초기화했다. AI 원본은 보존하고 확정값과 시각은 비워 뒀다.
- 두 번 제출해도 최초 확정본이 남도록 DB에서 검토 대기인 행만 갱신했다. 갱신 후 같은 트랜잭션에서 다시 읽었을 때도 확정값이 보이는지 테스트했다.

## 리뷰에서 바꾼 점

위험도가 잘못됐을 때 서버는 저장을 거절했지만, 오류 화면에서는 첫 선택지인 ‘정상’이 선택된 것처럼 보일 수 있었다. 다크 UI를 적용하면서 빈 값의 ‘위험도 선택’을 추가했다. 최초 검토 화면에는 AI 위험도를 표시하고, 오류 화면에는 사용자가 입력한 나머지 값과 오류 메시지를 유지했다.

개발 중 UI를 변경한 뒤 Chromium에서 다른 필드만 고쳐도 위험도를 선택하기 전까지 확정할 수 없음을 확인했다. 브라우저의 입력 검사를 건너뛴 요청도 서버가 400으로 거절했다.

PR #3 병합 전 사용자가 집 PC의 `feature/analysis-review`에서 두 가지 확정 흐름을 직접 실행하고 화면을 공유했다. AI 원본을 그대로 확정한 경우와 위험도·권장 조치를 바꿔 확정한 경우였다. 병합 후에는 사용자가 로컬 `main`을 업데이트하고 작업 트리와 커밋을 확인했다.

중간 저장과 확정본 직접 정정, 사용자 인증과 담당자별 확정 기록은 지원하지 않는다. [단계별 검증 결과](VERIFICATION.md)
