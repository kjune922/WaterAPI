# AI 분석 검토·확정 작업 기록

## 요청과 판단

사용자가 저장소 조사 계획을 검토하고, 점검일지 상세에서 AI 원본을 비교해 한 번에 수정·확정하는 구현을 승인했다.

- AI 응답은 기존 네 필드에 두고 사용자 확정값 네 개와 확정 시각을 같은 행에 저장했다. 점검일지 수정·삭제가 성공하면 해당 행 전체가 삭제되어 기존 트랜잭션 규칙이 적용된다.
- Flyway V2는 기존 분석을 검토 대기로 초기화한다. 기존 데이터에는 사용자 확정을 뒷받침하는 기록이 없기 때문이다.
- 분석 ID, 점검일지 ID, 검토 대기를 조건으로 한 번에 갱신한다. 변경 행 수가 1이면 성공하고, 0이면 대상 부재(404)와 이미 확정(409)을 구분한다. 갱신 전 JPA의 미반영 변경을 반영하고 갱신 후 영속성 컨텍스트를 비워 같은 트랜잭션의 재조회에서도 확정값을 읽게 했다.
- 폼과 서비스에서 입력을 검증한다. 기존 목록 필터와 대시보드 집계가 사용하는 원본 위험도를 화면에 ‘AI 분석 위험도’로 표시했다.

## 실제 검증

- Java 17에서 저장소 Gradle Wrapper로 `build mysqlTest` 성공. 일반 테스트 64건, 임시 MySQL 8.4.13 테스트 10건 통과. 실패·오류·건너뜀 각 0건. 실행 JAR 생성.
- H2·Stub과 MockMvc로 원본 보존, 수정·확정, 같은 트랜잭션 재조회, 중복 제출 시 최초 확정값·시각 보존, 입력 오류, 잘못된 점검일지 ID, 재분석 전의 오래된 폼 거절을 확인했다.
- MySQL에서 동시 확정 두 건 중 한 건만 성공했다. 확정 후 점검일지 수정·삭제가 성공하면 분석이 사라졌고, 트리거로 삭제 실패를 유도하면 점검일지와 확정 결과가 보존됐다.
- 별도 임시 스키마에서 Flyway V1 적용 → 샘플 분석 입력 → V2 적용과 JPA 스키마 검증을 실행했다. 기존 네 값과 분석 시각, 점검일지 연결이 보존되고 상태는 검토 대기, 확정 필드와 확정 시각은 모두 NULL이었다.
- 빌드한 JAR에 HTTP로 접속해 상세 화면과 대시보드, 결과 확정 후 상세로 이동, 중복 확정 409, AI 원본 위험도 필터를 확인했다.

## 남은 한계

중간 저장과 확정본 직접 정정은 현재 미지원이다. 사용자 인증 및 담당자별 확정 기록은 없다. 화면은 HTTP 응답과 MockMvc로 검증했으며 브라우저 시각 검사는 미실행이다.

## UI 개편과 위험도 오류 재검증

- 리뷰에서 위험도가 누락되거나 잘못된 경우 첫 선택지인 ‘정상’이 표시될 수 있음을 확인했다. 승인된 UI 개편에서 빈 값의 ‘위험도 선택’을 첫 항목으로 추가했다. 최초 검토 화면은 AI 위험도를 선택하고, 오류 화면은 제출한 다른 값과 필드 오류를 유지한다.
- 기존 Thymeleaf 화면에 공통 내비게이션과 다크 테마를 적용했다. 상세 화면은 점검 원문, AI 원본, 검토 폼 또는 사용자 확정본을 구분하며 목록과 대시보드는 AI 원본 위험도를 표시한다.
- 검토 회귀 테스트 8건, 이를 포함한 일반 테스트 67건 통과. 실패·오류·건너뜀 각 0건. Java 17에서 Gradle 빌드와 실행 JAR 생성 성공.
- 실제 Chromium에서 1440px와 390px 너비로 대시보드, 빈 목록과 데이터 목록, 시설·점검일지 등록 및 수정, 입력 오류, 검토 대기와 확정 완료를 확인했다. 위험도 최초값, 오류 후 빈 선택과 입력 보존, 다른 필드만 고친 재제출 차단, 브라우저 검증을 우회한 요청의 서버 400 응답을 확인했다.
- 두 너비에서 입력과 버튼의 키보드 포커스를 확인했다. 임시 H2에 넣은 공백 없는 한국어 점검 원문 2,000자, AI 요약 500자, 권장 조치 1,000자에서 카드와 페이지 너비를 측정했고, 좁은 화면에서는 넓은 표 안에서만 가로 스크롤됐다. 브라우저 검증에는 Stub을 사용했다.
